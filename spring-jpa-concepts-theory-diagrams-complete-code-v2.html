Transactions

Start with this idea: A transaction is a safety boundary around a business operation. Either the required database work is committed, or the transaction is rolled back according to its rules.

1. What problem does it solve?

Imagine creating an order and its payment record. If the order is saved but the payment fails, the database is left in an inconsistent state. A transaction lets us treat both operations as one unit.

2. Beginner mental model

Think of a transaction like a temporary agreement with the database: “I am doing several related changes. Do not permanently accept them until I finish successfully.”

flowchart TD
A["Business operation"] --> B["Begin / join transaction"]
B --> C["DB operation 1"]
C --> D["DB operation 2"]
D --> E{"Everything successful?"}
E -->|Yes| F["COMMIT — make changes permanent"]
E -->|No| G["ROLLBACK — undo uncommitted changes"]

3. What Spring adds

Spring lets the service layer define the transaction boundary, while a transaction manager handles the actual transaction lifecycle. In our project, @Transactional is intercepted by Spring and the JpaTransactionManager coordinates JPA.

Interview focus

Interview answer: “A transaction is a logical unit of work whose database changes are committed together or rolled back according to the transaction rules. In Spring, transaction management separates this concern from business logic through a transaction manager and declarative or programmatic transaction APIs.”

Interview trap: A transaction is not the same thing as a Java method. One transaction can contain calls to multiple methods/DAOs, depending on the transaction boundary.
Memory: Transaction = business unit + boundary + commit/rollback.

Programmatic Transaction

Simple idea: With a programmatic transaction, your code explicitly controls the transaction API instead of relying only on @Transactional.

Why would we use it?

Most business services prefer declarative transactions because they are cleaner. Programmatic transactions are useful when the transaction behavior must be decided dynamically or when explicit transaction control is genuinely required.

flowchart LR
S["Service code"] --> T["TransactionTemplate"]
T --> W["Transactional callback"]
W --> D["DAO / Repository"]
D --> DB[("Database")]
T --> R["Commit / Rollback"]
transactionTemplate.execute(status -> {
    try {
        dao.save();
        return null;
    } catch (RuntimeException ex) {
        status.setRollbackOnly();
        throw ex;
    }
});

Interview focus

Answer: “Programmatic transaction management means the application explicitly uses Spring transaction APIs such as TransactionTemplate or a transaction manager. It gives more control but adds transaction-handling code, so declarative transactions are usually preferred for normal service methods.”

Trap: Do not confuse EntityManager.getTransaction() with Spring-managed transaction control. In a Spring application using JpaTransactionManager, let Spring manage the transaction boundary.
Memory: Programmatic = I control it in code.

Declarative Transaction

Simple idea: Declarative means tell Spring the transaction rule; Spring performs the transaction work for you.

Why is this useful?

Business code should focus on “transfer money”, “place order”, or “create employee”, not on repeatedly writing begin/commit/rollback boilerplate.

sequenceDiagram
participant C as Caller
participant P as Spring Proxy
participant T as TransactionManager
participant S as Service
C->>P: call service()
P->>T: begin / join
P->>S: execute business logic
S-->>P: result or exception
P->>T: commit / rollback
P-->>C: return

Two styles in this guide

  • XML: transaction infrastructure/rules are configured in Spring XML.
  • @Transactional: transaction rules are declared close to the service method.

Interview focus

Answer: “Declarative transaction management defines transaction behavior through configuration or annotations. Spring's transaction infrastructure applies that behavior around the target method, usually through an interceptor/proxy and a transaction manager.”

Memory: Declarative = declare the rule, Spring does the plumbing.

Declarative Transaction — XML

Simple idea: XML is the older/classic configuration style for telling Spring which transaction infrastructure to enable and how it should be applied.
flowchart TD
X["Spring XML"] --> A["Transaction configuration / advice"]
A --> P["Spring proxy / interceptor"]
P --> S["Service method"]
A --> T["TransactionManager"]

What you should understand for interviews

You do not need to memorize every XML attribute. Know the relationship: XML config → transaction advice/interception → transaction manager → service execution.

<tx:annotation-driven transaction-manager="transactionManager"/>

Interview focus

Answer: “In XML-based Spring configuration, transaction infrastructure is declared in the application context. Spring then applies transaction advice through its AOP/interception mechanism and delegates transaction work to the configured transaction manager.”

Trap: XML configuration and @Transactional are both declarative styles; they are not two different transaction mechanisms underneath. Both ultimately use Spring's transaction infrastructure.

Declarative Transaction — @Transactional

Simple idea: @Transactional says: “Run this service operation inside a Spring-managed transaction with these rules.”
sequenceDiagram
participant C as Caller
participant P as Proxy
participant T as TxManager
participant S as Service
C->>P: addEmployee()
P->>T: begin / join
P->>S: addEmployee()
S-->>P: success / exception
P->>T: commit / rollback
P-->>C: result

Important attributes

The interview-relevant ones in this guide are propagation, readOnly, timeout, rollbackFor, and noRollbackFor.

@Transactional(
    propagation = Propagation.REQUIRED,
    readOnly = false,
    timeout = 10,
    rollbackFor = Exception.class
)
public void createEmployee() { }

Interview focus

Answer: “@Transactional is a declarative way to define transaction semantics on a Spring-managed method or class. Spring's transaction interceptor uses the annotation metadata to begin, join, commit, or roll back a transaction through the configured transaction manager.”

Trap: @Transactional is not magic inside the method itself. In proxy-based Spring configuration, the call normally has to pass through the Spring proxy for the interceptor to apply.

PlatformTransactionManager

Simple idea: PlatformTransactionManager is the common Spring interface for transaction management. Your service can depend on the abstraction instead of hard-coding one transaction technology.
flowchart TD
P["PlatformTransactionManager
Spring abstraction"] --> J["JpaTransactionManager"]
P --> D["DataSourceTransactionManager"]
P --> G["JtaTransactionManager"]

Why do we need an abstraction?

Spring wants the transaction-facing application code to be independent of the exact resource technology. The concrete manager knows how to talk to JPA, JDBC, or JTA.

Interview focus

Answer: “PlatformTransactionManager is Spring's central transaction-management abstraction. Concrete implementations such as JpaTransactionManager provide the technology-specific transaction behavior.”

Memory: Platform = interface; implementation = technology-specific manager.

JpaTransactionManager

Simple idea: JpaTransactionManager is the Spring transaction manager used for a JPA persistence unit in a typical single-database application.
flowchart LR
TM["JpaTransactionManager"] --> EMF["EntityManagerFactory"]
EMF --> EM["EntityManager"]
EM --> PC["Persistence Context"]
PC --> DB[("Database")]
TM -. "transaction boundary" .-> DB

What happens in our project?

applicationContext.xml creates the JpaTransactionManager and gives it the EntityManagerFactory. When a transactional service method runs, Spring uses this manager to coordinate the JPA transaction.

Interview focus

Answer: “JpaTransactionManager is Spring's PlatformTransactionManager implementation for JPA. It integrates Spring transaction management with the JPA EntityManagerFactory and persistence context.”

Trap: JPA is the persistence specification/API; Hibernate is one JPA implementation. JpaTransactionManager is Spring's transaction manager, not Hibernate itself.

Transactional Proxy

Simple idea: The proxy is the middleman around your service. It can start/join the transaction before the method and commit/roll back after it.
sequenceDiagram
participant C as Caller
participant P as Spring Proxy
participant T as TransactionManager
participant S as Target Service
C->>P: service.operation()
P->>T: begin / join
P->>S: operation()
S-->>P: return / exception
P->>T: commit / rollback
P-->>C: result / exception

Why should you care?

This explains a common interview question: @Transactional is usually applied by Spring's interception/proxy mechanism, not by the annotation executing code itself.

Self-invocation trap

If one method calls another transactional method through this.otherMethod(), the call can bypass the proxy. That means the second method's proxy-based transaction advice may not run as you expect.

Interview focus

Answer: “Spring can create a transaction-aware proxy around a bean. The proxy intercepts an external call, applies the transaction policy, invokes the target, and then commits or rolls back through the transaction manager.”

Memory: Caller → Proxy → Transaction → Target method.

Persistence Context

Simple idea: A persistence context is the managed world of JPA entities associated with an EntityManager. JPA tracks managed entity state so changes can be synchronized with the database.
stateDiagram-v2
[*] --> Transient
Transient --> Managed: persist()
Managed --> Detached: clear / close
Detached --> Managed: merge()
Managed --> Removed: remove()
Removed --> [*]

Why is this important?

If an entity is managed, you often do not need to call an explicit update method. You change the managed object and JPA can detect the change and synchronize it during flush/transaction completion.

EmployeeEntity e = entityManager.find(EmployeeEntity.class, id);
e.setSalary(90000.0);
// If e is managed, JPA can detect the change during flush.

Interview focus

Answer: “The persistence context is JPA's first-level managed entity context. It keeps track of entity instances and their state, provides identity guarantees within the context, and participates in dirty checking and synchronization with the database.”

Trap: Persistence context is not the same thing as the database. An entity can be managed in memory before its change is actually synchronized to the database.

Local Transaction

Beginner idea: LOCAL = one transactional resource. In a normal Spring + JPA application using one database, the transaction is usually local to that database.

Example

Our employee application writes department and employee data to the same database. One database transaction can commit both operations together or roll them back together.

flowchart LR
S["Service"] --> TM["JpaTransactionManager"]
TM --> DB[("One database")]
DB --> C["COMMIT / ROLLBACK"]

Why is local usually preferred?

It is simpler: fewer moving parts, easier configuration, and usually enough when all required changes belong to one database resource.

Interview focus

Answer: “A local transaction is managed for a specific transactional resource, such as one database. For a typical single-database JPA application, JpaTransactionManager can manage that local transaction.”

Trap: Local does not mean “no transaction” or “one SQL statement”. A local transaction can contain many SQL statements against the same resource.
Memory: Local = one resource, one transaction boundary.

Global Transaction

Beginner idea: GLOBAL = coordinate multiple transactional resources. The classic example is a business operation that must coordinate more than one resource, such as a database and a messaging resource.
flowchart TD
A["Application"] --> T["JTA / global transaction coordinator"]
T --> DB["Database"]
T --> MQ["Messaging resource"]
T --> R["Other transactional resource"]
T -. "coordinate outcome" .-> DB
T -. "coordinate outcome" .-> MQ

Why not just use two local transactions?

Two independent local transactions can produce a partial result: resource A commits while resource B fails. A global transaction model exists to coordinate resources when the business requirement truly needs one distributed transaction outcome.

Interview focus

Answer: “A global transaction coordinates multiple transactional resources. In Spring, JtaTransactionManager integrates Spring with JTA for distributed transaction coordination. It is more complex than a local single-resource transaction and should be used when the architecture actually requires distributed transaction semantics.”

Trap: Do not say “global transaction is always better.” It introduces distributed coordination and operational complexity. For one database, a local transaction is normally simpler.
Memory: Local = one resource. Global = multiple resources coordinated.

Propagation — REQUIRED

Simple idea: REQUIRED means use the current transaction if there is one; otherwise create one. It is the common/default propagation choice.
flowchart TD
A["Enter method"] --> B{"Transaction exists?"}
B -->|Yes| C["Join existing transaction"]
B -->|No| D["Create new transaction"]
@Transactional(propagation = Propagation.REQUIRED)
public void createOrder() { }

Interview scenario

Service A is already transactional and calls Service B with REQUIRED. B normally participates in A's transaction. If B is called without an active transaction, Spring creates one for B.

Interview answer: “REQUIRED joins an existing transaction if available; otherwise it starts a new transaction.”

REQUIRED = join or create.

Propagation — REQUIRES_NEW

Simple idea: REQUIRES_NEW says this method needs its own transaction. An existing transaction is suspended while the new transaction runs.
sequenceDiagram
participant O as Outer Tx
participant S as Service
participant N as New Tx
O->>S: call REQUIRES_NEW
S-->>O: suspend outer
S->>N: BEGIN new transaction
N->>N: independent work
N-->>S: COMMIT / ROLLBACK
S-->>O: resume outer

Common interview example

An audit record may need to commit independently from the main operation. If the audit operation is intentionally independent, REQUIRES_NEW can provide that separate transaction.

Interview answer: “REQUIRES_NEW suspends the existing transaction and starts an independent transaction for the method.”

Trap: Independent transaction does not mean “no transaction”. It means a separate transaction.

Propagation — MANDATORY

Simple idea: MANDATORY means “I refuse to run unless the caller already started a transaction.”
flowchart TD
A["Enter method"] --> B{"Transaction exists?"}
B -->|Yes| C["Join existing"]
B -->|No| D["Throw exception"]

Why use it?

It is useful when a lower-level operation is only valid as part of a larger business transaction and should never accidentally run alone.

Interview answer: “MANDATORY requires an existing transaction and throws an exception if none exists.”

MANDATORY = transaction must already be there.

Propagation — NEVER

Simple idea: NEVER is the opposite kind of rule: “I must not run inside a transaction.”
flowchart TD
A["Enter method"] --> B{"Transaction exists?"}
B -->|No| C["Execute without transaction"]
B -->|Yes| D["Reject invocation"]

Interview answer: “NEVER requires that no transaction be active; if one exists, Spring throws an exception.”

Trap: NEVER is not the same as NOT_SUPPORTED. NEVER rejects an active transaction; NOT_SUPPORTED suspends it and then runs.

Propagation — NOT_SUPPORTED

Simple idea: NOT_SUPPORTED means run without a transaction. If a transaction already exists, Spring suspends it for this method.
sequenceDiagram
participant O as Outer Tx
participant S as NOT_SUPPORTED method
O->>S: invoke
S-->>O: suspend outer transaction
S->>S: execute without transaction
S-->>O: resume outer transaction

Interview answer: “NOT_SUPPORTED executes non-transactionally and suspends an existing transaction for the duration of the method.”

Compare: NEVER = reject if a transaction exists. NOT_SUPPORTED = suspend it and continue.

Propagation — SUPPORTS

Simple idea: SUPPORTS means “use a transaction if the caller already has one; otherwise I can run without one.”
flowchart TD
A["Enter method"] --> B{"Transaction exists?"}
B -->|Yes| C["Participate in it"]
B -->|No| D["Run without transaction"]

Interview answer: “SUPPORTS participates in the current transaction if one exists; otherwise it executes without a transaction.”

SUPPORTS = optional transaction.

Propagation — NESTED

Simple idea: NESTED means nested work can use savepoint-style rollback when the transaction manager/resource supports it.
flowchart TD
A["Outer transaction"] --> B["Create savepoint"]
B --> C["Nested work"]
C --> D{"Nested failure?"}
D -->|No| E["Continue outer transaction"]
D -->|Yes| F["Rollback to savepoint"]
F --> E

Interview focus

The key distinction is that NESTED is about nested/savepoint semantics inside an existing transaction, not simply starting a totally independent transaction.

Interview answer: “NESTED uses a nested transaction/savepoint model when supported, allowing inner work to roll back to a savepoint while the outer transaction can continue.”

Trap: Do not claim every transaction manager/resource supports identical NESTED behavior. Support depends on the underlying transaction infrastructure.

Rollback

Simple idea: Rollback means do not make the transaction's uncommitted database changes permanent.
flowchart TD
A["BEGIN"] --> B["Operation 1"]
B --> C["Operation 2"]
C --> D["Failure / rollback decision"]
D --> E["ROLLBACK"]
E --> F["Transaction ends without commit"]

When does Spring decide?

For declarative transactions, Spring evaluates the exception against its rollback rules. By default, unchecked exceptions trigger rollback; checked exceptions do not automatically trigger rollback.

Interview answer: “Rollback ends the transaction without committing its transactional changes. In Spring, whether an exception causes rollback depends on the configured rollback rules.”

Rollback = do not commit this transaction.

Rollback — RuntimeException

Simple idea: By default, Spring's declarative transaction rules normally roll back for unchecked exceptions such as RuntimeException.
flowchart TD
A["@Transactional"] --> B["DB changes"] --> C["RuntimeException"] --> D["Rollback"]
@Transactional
public void save() {
    dao.insert();
    throw new RuntimeException("failure");
}

Interview answer: “Spring's default rollback rules include RuntimeException and Error, so an unchecked exception normally causes rollback for a declarative transaction.”

Trap: Saying “any exception causes rollback by default” is too broad.

Rollback — CheckedException

Simple idea: A checked exception such as Exception does not automatically mean rollback under Spring's default rollback rules.
flowchart TD
A["@Transactional"] --> B["DB changes"] --> C["Checked exception"] --> D{"Rollback rule configured?"}
D -->|No| E["No default rollback"]
D -->|Yes| F["Rollback"]
@Transactional
public void process() throws Exception {
    dao.insert();
    throw new Exception("checked failure");
}

Interview answer: “Checked exceptions do not trigger rollback by default in Spring's standard declarative rules; use an explicit rollback rule when required.”

RuntimeException → default rollback. Checked Exception → configure if needed.

rollbackFor

Simple idea: rollbackFor says “also roll back when this exception type occurs.”
flowchart LR
A["Checked exception"] --> B["rollbackFor"] --> C["Rollback rule"] --> D["ROLLBACK"]
@Transactional(rollbackFor = Exception.class)
public void process() throws Exception {
    dao.insert();
    throw new Exception("failure");
}

Interview answer: “rollbackFor lets us explicitly include exception types in the rollback rules, which is commonly used when a checked exception must cause rollback.”

Trap: rollbackFor is a rule definition; it does not itself perform a rollback immediately.

noRollbackFor

Simple idea: noRollbackFor says “this exception should not trigger rollback under the configured rule.”
flowchart LR
A["Configured exception"] --> B["noRollbackFor"] --> C["No rollback rule for it"] --> D["Transaction may commit"]
@Transactional(noRollbackFor = WarningException.class)
public void process() {
    dao.insert();
    throw new WarningException();
}

Interview answer: “noRollbackFor lets us exclude selected exception types from the transaction's rollback rules.”

Trap: The method still throws the exception. noRollbackFor controls rollback behavior; it does not swallow the exception.

readOnly

Simple idea: readOnly=true tells Spring and the underlying transaction/persistence infrastructure that the transaction is intended for reading.
flowchart LR
S["Read service"] --> A["@Transactional(readOnly=true)"]
A --> T["Transaction infrastructure"]
T --> Q["Read operations"]

Why use it?

It documents intent and can allow optimizations depending on the transaction manager and persistence provider.

@Transactional(readOnly = true)
public List<EmployeeDTO> findEmployees() {
    return repository.findAll();
}

Interview answer: “readOnly expresses that a transaction is intended for read operations and may allow persistence-provider or infrastructure optimizations. It should not be treated as a universal write-blocking guarantee.”

Trap: Do not say readOnly=true is a security mechanism that guarantees no write can ever happen.

timeout

Simple idea: A transaction timeout puts a time limit on transaction execution. If the limit is exceeded, the transaction infrastructure can mark the transaction for timeout/rollback according to the environment.
flowchart TD
A["Transaction begins"] --> B["Work"] --> C{"Timeout exceeded?"}
C -->|No| D["Commit"]
C -->|Yes| E["Timeout outcome / rollback"]
@Transactional(timeout = 10)
public void processOrder() {
    // Transaction should not run indefinitely.
}

Interview answer: “timeout defines how long a transaction is allowed to run before the transaction infrastructure treats it as timed out.”

Trap: A transaction timeout is not the same as a socket/request timeout. They belong to different layers.

Spring Data JPA — CrudRepository

Simple idea: CrudRepository gives you common CRUD operations without writing the basic repository implementation yourself.
flowchart LR
S["Service"] --> R["CrudRepository"]
R --> G["Spring Data generated implementation"]
G --> J["JPA"]
J --> DB[("Database")]

What do you get?

Typical CRUD operations include save, find, findAll, exists, count and delete operations. Spring Data creates the repository implementation at runtime.

public interface EmployeeRepository
        extends CrudRepository<EmployeeEntity, Integer> {
}

// Then the service can use repository.save(...),
// findById(...), findAll(), deleteById(...), etc.

Interview answer: “CrudRepository is a Spring Data repository abstraction that provides standard CRUD operations and removes the need to implement those basic data-access methods manually.”

CrudRepository = ready-made CRUD contract.

Spring Data JPA — RepositoryDefinition

Simple idea: @RepositoryDefinition lets you define a repository interface by declaring its domain and ID types without extending a Spring Data repository interface.
flowchart LR
I["Repository interface"] --> A["@RepositoryDefinition"]
A --> S["Spring Data repository infrastructure"]
S --> J["JPA"]

@RepositoryDefinition(
    domainClass = EmployeeEntity.class,
    idClass = Integer.class)
public interface EmployeeReadRepository {

    EmployeeEntity findById(Integer id);
}

Interview focus

The useful distinction is: extending CrudRepository gives you inherited CRUD methods; @RepositoryDefinition lets you expose only the methods you declare while still participating in Spring Data repository infrastructure.

Interview answer: “@RepositoryDefinition defines a Spring Data repository without extending one of the repository interfaces, allowing the developer to declare the repository methods explicitly.”

Spring Data JPA — Query Method

Simple idea: A query method lets Spring Data derive the query from the method name.
flowchart LR
M["findBySalaryGreaterThanEqualAndRole"] --> P["Spring Data parses method name"]
P --> Q["Derived query"]
Q --> J["JPA"]
J --> DB[("Database")]

List<EmployeeEntity>
findBySalaryGreaterThanEqualAndRole(
    Double salary,
    String role);

How to read the name

findBy starts the query. SalaryGreaterThanEqual becomes a salary comparison. AndRole adds another condition.

Interview answer: “Spring Data parses supported repository method-name keywords and derives the query from them. It is convenient for simple-to-moderate queries.”

Trap: If the method name becomes extremely long or the query is complex, @Query or another query mechanism may be clearer.

Spring Data JPA — @Query

Simple idea: @Query means you write the query explicitly instead of asking Spring Data to derive it from the method name.
flowchart LR
A["Repository method"] --> Q["@Query JPQL"]
Q --> J["JPA provider"]
J --> DB[("Database")]

@Query("""
    SELECT e
    FROM EmployeeEntity e
    WHERE e.salary >= :salary
    """)
List<EmployeeEntity> findEmployees(
    @Param("salary") Double salary);

JPQL interview point

JPQL normally refers to entity classes and entity fields, not directly to database table/column names.

Interview answer: “@Query lets us define a JPQL query explicitly on a repository method when method-name derivation is not appropriate or readable enough.”

Query Method = Spring derives. @Query = I specify.

Positional Parameters

Simple idea: A positional parameter identifies the query value by its argument position. ?1 means the first method argument.
flowchart LR
P["?1"] --> A["First method parameter"] --> Q["JPQL binding"]

@Query("SELECT e FROM EmployeeEntity e WHERE e.salary >= ?1")
List<EmployeeEntity> findBySalary(Double salary);

Interview answer: “Positional parameters use numbered placeholders such as ?1, ?2 and bind arguments according to their method position.”

Trade-off: They are short, but changing parameter order can make the query harder to maintain. Named parameters are often clearer for complex queries.

Named Parameters

Simple idea: A named parameter identifies a value by a readable name, such as :salary.
flowchart LR
N[":salary"] --> P["@Param('salary')"] --> Q["JPQL binding"]

@Query("SELECT e FROM EmployeeEntity e WHERE e.salary >= :salary")
List<EmployeeEntity> findBySalary(
    @Param("salary") Double salary);

Interview answer: “Named parameters use a readable JPQL name such as :salary and bind it to a repository method argument, commonly with @Param.”

?1 = position. :salary = meaning.

@Modifying

Simple idea: @Modifying tells Spring Data JPA that an @Query method performs a modifying statement such as UPDATE or DELETE, rather than a SELECT.
flowchart LR
S["Transactional service"] --> R["Repository"]
R --> M["@Modifying + @Query"]
M --> DB[("UPDATE / DELETE")]

@Modifying
@Query("""
    UPDATE EmployeeEntity e
    SET e.salary = :salary
    WHERE e.role = :role
    """)
int updateSalaryByRole(
    @Param("role") String role,
    @Param("salary") Double salary);

Interview focus

Bulk update/delete queries are different from normal entity-select queries. They should be executed within an appropriate transaction.

Interview answer: “@Modifying is used with Spring Data JPA query methods that modify data, such as UPDATE and DELETE. Such operations normally need a transaction.”

Trap: @Modifying does not itself mean “start a transaction.” Transaction management is a separate concern, commonly supplied by @Transactional.

orm.xml

Simple idea: orm.xml is a JPA mapping/metadata file that can externalize ORM metadata. In this guide, it is used to demonstrate an external named query.
flowchart LR
X["META-INF/orm.xml"] --> N["Named query / ORM metadata"]
N --> J["JPA provider"]
J --> DB[("Database")]

<named-query name="Employee.findSeniorEmployees">
    <query>
        SELECT e FROM EmployeeEntity e
        WHERE e.role = 'Senior Developer'
    </query>
</named-query>

Why learn it?

Modern Spring Data projects often keep query logic in repository annotations or methods, but orm.xml is still useful to understand because JPA supports external ORM metadata and named queries.

Interview answer: “orm.xml is a JPA ORM metadata file. It can define mapping metadata and named queries outside the entity source code.”

Trap: Do not describe orm.xml as a Spring Data-specific file. It belongs to JPA ORM metadata.

package com.example.employee.dao;

import com.example.employee.dto.EmployeeDTO;
import com.example.employee.entity.DepartmentEntity;
import com.example.employee.entity.EmployeeEntity;
import jakarta.persistence.EntityManager;
import jakarta.persistence.PersistenceContext;
import org.springframework.stereotype.Repository;
import java.time.LocalDate;
import java.util.List;

@Repository
public class EmployeeDAOImpl implements EmployeeDAO {

    /*
     * Spring injects a container-managed EntityManager.
     * Do not manually call getTransaction().begin().
     */
    @PersistenceContext
    private EntityManager entityManager;

    @Override
    public Integer addEmployee(EmployeeDTO dto) {

        // Convert DTO into the JPA entity.
        EmployeeEntity entity = new EmployeeEntity();
        entity.setName(dto.getName());
        entity.setRole(dto.getRole());
        entity.setSalary(dto.getSalary());
        entity.setJoiningDate(dto.getJoiningDate());

        if (dto.getDepartmentId() != null) {

            // Obtain a managed reference to the department.
            DepartmentEntity department =
                entityManager.getReference(
                    DepartmentEntity.class,
                    dto.getDepartmentId());

            entity.setDepartment(department);
        }

        // New entity becomes managed.
        entityManager.persist(entity);

        return entity.getEmployeeId();
    }

    @Override
    public List<EmployeeEntity> findByJoiningDate(
            LocalDate start, LocalDate end) {

        String jpql = """
            SELECT e
            FROM EmployeeEntity e
            WHERE e.joiningDate BETWEEN :start AND :end
            ORDER BY e.name
            """;

        return entityManager
            .createQuery(jpql, EmployeeEntity.class)
            .setParameter("start", start)
            .setParameter("end", end)
            .getResultList();
    }

    @Override
    public int updateSalaryByRole(
            String role, Double salary) {

        return entityManager.createQuery("""
            UPDATE EmployeeEntity e
            SET e.salary = :salary
            WHERE e.role = :role
            """)
            .setParameter("salary", salary)
            .setParameter("role", role)
            .executeUpdate();
    }

    @Override
    public int deleteByName(String name) {

        return entityManager.createQuery("""
            DELETE FROM EmployeeEntity e
            WHERE e.name = :name
            """)
            .setParameter("name", name)
            .executeUpdate();
    }
}

package com.example.employee.dao;

import com.example.employee.dto.EmployeeDTO;
import com.example.employee.entity.EmployeeEntity;
import org.springframework.stereotype.Component;
import java.time.LocalDate;
import java.util.List;

@Component
public class EmployeeDAOWrapper {

    private final EmployeeDAO dao;

    public EmployeeDAOWrapper(EmployeeDAO dao) {
        this.dao = dao;
    }

    // Wrapper keeps DTO/entity conversion outside the service.
    public Integer addEmployee(EmployeeDTO dto) {
        return dao.addEmployee(dto);
    }

    public List<EmployeeDTO> findByJoiningDate(
            LocalDate start, LocalDate end) {

        return dao.findByJoiningDate(start, end)
            .stream()
            .map(this::toDTO)
            .toList();
    }

    public int updateSalaryByRole(
            String role, Double salary) {
        return dao.updateSalaryByRole(role, salary);
    }

    public int deleteByName(String name) {
        return dao.deleteByName(name);
    }

    private EmployeeDTO toDTO(EmployeeEntity entity) {

        EmployeeDTO dto = new EmployeeDTO();
        dto.setEmployeeId(entity.getEmployeeId());
        dto.setName(entity.getName());
        dto.setRole(entity.getRole());
        dto.setSalary(entity.getSalary());
        dto.setJoiningDate(entity.getJoiningDate());

        if (entity.getDepartment() != null) {
            dto.setDepartmentId(
                entity.getDepartment().getDepartmentId());
        }

        return dto;
    }
}

import org.springframework.stereotype.Service;
import org.springframework.transaction.PlatformTransactionManager;
import org.springframework.transaction.support.TransactionTemplate;
import org.springframework.transaction.annotation.*;

import java.time.LocalDate;
import java.util.List;

@Service
public class EmployeeServiceImpl
        implements EmployeeService {

    private final EmployeeDAOWrapper employeeDAO;
    private final DepartmentDAO departmentDAO;
    private final EmployeeRepository repository;

    /*
     * Programmatic transaction support.
     * We depend on Spring's common transaction abstraction.
     */
    private final TransactionTemplate transactionTemplate;

    public EmployeeServiceImpl(
            EmployeeDAOWrapper employeeDAO,
            DepartmentDAO departmentDAO,
            EmployeeRepository repository,
            PlatformTransactionManager transactionManager) {

        this.employeeDAO = employeeDAO;
        this.departmentDAO = departmentDAO;
        this.repository = repository;

        this.transactionTemplate =
            new TransactionTemplate(transactionManager);
    }

    @Override
    @Transactional
    public Integer addEmployee(EmployeeDTO dto) {

        validate(dto);

        return employeeDAO.addEmployee(dto);
    }

    @Override
    @Transactional(readOnly = true)
    public List<EmployeeDTO> findEmployees(
            LocalDate start, LocalDate end) {

        return employeeDAO.findByJoiningDate(
            start, end);
    }

    @Override
    @Transactional
    public int updateSalaryByRole(
            String role, Double salary) {

        return repository.updateSalaryByRole(
            role, salary);
    }

    @Override
    @Transactional
    public int deleteByName(String name) {
        return repository.deleteByName(name);
    }

    /*
     * REQUIRED is the normal/default propagation.
     * Both DAO operations participate in this transaction.
     */
    @Override
    @Transactional(propagation = Propagation.REQUIRED)
    public void createDepartmentWithEmployee(
            String departmentName,
            EmployeeDTO employee) {

        Integer departmentId =
            departmentDAO.addDepartment(
                new DepartmentDTO(departmentName));

        employee.setDepartmentId(departmentId);

        employeeDAO.addEmployee(employee);

        /*
         * Uncomment to demonstrate rollback of BOTH operations:
         *
         * throw new RuntimeException("Demo failure");
         */
    }

    /*
     * PROGRAMMATIC TRANSACTION:
     * No @Transactional is required for this method.
     * The code explicitly executes a transactional callback.
     */
    @Override
    public void demonstrateProgrammaticTransaction(
            EmployeeDTO employee) {

        transactionTemplate.execute(status -> {

            try {

                employeeDAO.addEmployee(employee);

                // Additional DAO operations can be included here.

                return null;

            } catch (RuntimeException ex) {

                // Explicit programmatic rollback request.
                status.setRollbackOnly();

                throw ex;
            }
        });
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void requiresNewOperation() {
        // Suspend outer transaction and start a new one.
    }

    @Transactional(propagation = Propagation.MANDATORY)
    public void mandatoryOperation() {
        // Transaction must already exist.
    }

    @Transactional(propagation = Propagation.NEVER)
    public void neverOperation() {
        // Transaction must not exist.
    }

    @Transactional(propagation = Propagation.NOT_SUPPORTED)
    public void notSupportedOperation() {
        // Suspend outer transaction and execute without one.
    }

    @Transactional(propagation = Propagation.SUPPORTS)
    public void supportsOperation() {
        // Participate if a transaction exists.
    }

    @Transactional(propagation = Propagation.NESTED)
    public void nestedOperation() {
        // Savepoint/nested semantics where supported.
    }

Scenario 01: Two DAOs, one transaction, second DAO fails

Scenario: A service has @Transactional. DAO-A inserts an employee successfully. DAO-B then throws a RuntimeException. What happens?

Answer: If both DAO calls execute inside the same transaction, the transaction is marked for rollback and the earlier DAO-A change is not committed. The transaction is the boundary, not each DAO call.

flowchart LR
S["Service @Transactional"] --> A["DAO A: INSERT"]
A --> B["DAO B: failure"]
B --> R["ROLLBACK"]
R --> X["DAO A change not committed"]

Interview line: “The transaction boundary is normally at the service layer, so both DAO operations participate in the same unit of work.”

Scenario 02: RuntimeException is caught inside the transaction

Scenario: A transactional method catches a RuntimeException and does not rethrow it. Will Spring automatically roll back?

Answer: Do not assume it will. If the exception does not escape the transactional method, Spring's interceptor may see a normal return and commit. If the business rule requires rollback, explicitly mark the transaction rollback-only or rethrow an appropriate exception.

@Transactional
public void process() {
    try {
        dao.save();
        throw new RuntimeException("failure");
    } catch (RuntimeException ex) {
        // If you intentionally swallow it, Spring may see normal completion.
        // status.setRollbackOnly() is one explicit rollback option.
    }
}

Scenario 03: Why put @Transactional on the service layer?

Scenario: An interviewer asks why transactions are commonly placed on services rather than individual DAO methods.

Answer: A service represents a business use case and may call several DAOs/repositories. Putting the transaction around the service lets all those operations succeed or fail as one business unit.

flowchart TD
C["Controller"] --> S["@Transactional Service"]
S --> A["DAO A"]
S --> B["DAO B"]
S --> R["Repository"]
A --> DB[("Database")]
B --> DB
R --> DB

Scenario 04: You manually call EntityManager.getTransaction()

Scenario: A developer writes entityManager.getTransaction().begin() inside a Spring-managed DAO. Is this the recommended approach?

Answer: No. With Spring-managed JPA transactions, let Spring's transaction manager control the transaction. Manual resource-level transaction handling mixes two transaction-management models and can cause errors.

Interview trap: RESOURCE_LOCAL in persistence.xml does not mean “manually begin transactions inside every DAO” when Spring is managing the EntityManager.

Scenario 05: TransactionTemplate or @Transactional?

Scenario: An interviewer asks when you would use programmatic transactions instead of @Transactional.

Answer: Prefer declarative transactions for normal business methods because they keep transaction policy separate from business logic. Use programmatic transaction management when the transaction behavior itself must be controlled dynamically in code or when a precise transactional callback is useful.

transactionTemplate.execute(status -> {
    // Explicit transactional callback.
    dao.save();
    return null;
});

Scenario 06: @Transactional is not working

Scenario: You added @Transactional, but the expected transaction behavior is not happening. What do you check first?

Answer: Check that the class is Spring-managed, transaction infrastructure is enabled, the correct transaction manager is configured, and the call passes through the Spring proxy. Also check for self-invocation and incorrect transaction configuration.

A["@Transactional"] --> B{"Spring bean?"}
B -->|No| X["Annotation not applied by Spring"]
B -->|Yes| C{"Proxy interception?"}
C -->|No| Y["Check self-invocation/config"]
C -->|Yes| D["Check transaction manager"]

Scenario 07: Self-invocation bypasses the proxy

Scenario: Method A calls this.methodB(), and methodB has @Transactional(REQUIRES_NEW). Will you automatically get a new transaction?

Answer: With proxy-based Spring transaction management, direct self-invocation does not pass through the proxy, so the transactional interceptor may not run for methodB. A common fix is to move the transactional method to another Spring bean or otherwise ensure the call crosses the proxy boundary.

Scenario 08: REQUIRED called from REQUIRED

Scenario: Outer service method is REQUIRED and calls an inner method also configured as REQUIRED. How many transactions?

Answer: Normally one transaction. The inner method joins the existing transaction instead of creating another independent transaction.

flowchart LR
A["Outer REQUIRED"] --> T["Transaction A"]
T --> B["Inner REQUIRED joins A"]

Scenario 09: REQUIRES_NEW inside REQUIRED

Scenario: Outer method uses REQUIRED. It calls an inner method using REQUIRES_NEW. What happens?

Answer: The outer transaction is suspended and a new transaction starts for the inner method. After the inner transaction completes, the outer transaction resumes.

sequenceDiagram
participant O as Outer Tx
participant I as Inner Tx
O->>I: suspend outer
I->>I: independent work
I-->>O: commit/rollback inner
O->>O: resume

Scenario 10: REQUIRES_NEW commits, then outer fails

Scenario: An audit method uses REQUIRES_NEW. It commits successfully. The outer transaction then throws a RuntimeException. Is the audit record rolled back?

Answer: No. The inner transaction already committed independently. The outer transaction can roll back without undoing that separate committed transaction.

flowchart TD
A["Outer Tx"] --> B["REQUIRES_NEW"]
B --> C["Inner COMMIT"]
C --> D["Outer resumes"]
D --> E["Outer ROLLBACK"]
C --> F["Audit remains committed"]

Scenario 11: REQUIRES_NEW fails

Scenario: The inner REQUIRES_NEW transaction fails. Does that automatically mean the outer transaction must roll back?

Answer: Not inherently. The inner transaction is separate. Its failure rolls back the inner transaction according to its rollback rules. The outer transaction's result depends on how the outer method handles the exception and its own transaction rules.

Scenario 12: MANDATORY called without a transaction

Scenario: A method is configured with MANDATORY, but the caller has no transaction.

Answer: Spring rejects the invocation because MANDATORY requires an existing transaction. It does not create one.

flowchart TD
A["Call MANDATORY"] --> B{"Existing Tx?"}
B -->|No| C["Reject / transaction-required exception"]
B -->|Yes| D["Join existing Tx"]

Scenario 13: NEVER called inside a transaction

Scenario: A method is configured with NEVER and is called from a transactional service.

Answer: The propagation rule rejects the call because NEVER requires that no transaction be active.

Scenario 14: NOT_SUPPORTED inside a transaction

Scenario: An outer operation has a transaction. A reporting method uses NOT_SUPPORTED.

Answer: The current transaction is suspended for that method, which runs without a transaction. Afterward the outer transaction resumes.

Scenario 15: SUPPORTS with and without a transaction

Scenario: A method uses SUPPORTS. What changes depending on the caller?

Answer: If a transaction exists, the method participates in it. If none exists, it can run without a transaction. SUPPORTS is therefore flexible rather than transaction-creating by itself.

Scenario 16: NESTED failure

Scenario: An outer transaction invokes a NESTED operation and the nested work fails.

Answer: Where nested/savepoint semantics are supported, the nested operation can roll back to a savepoint while allowing the outer transaction to continue. Do not equate NESTED with REQUIRES_NEW: NESTED is about savepoint-style behavior within the outer transaction.

flowchart TD
A["Outer Tx"] --> B["Savepoint"]
B --> C["Nested work fails"]
C --> D["Rollback to savepoint"]
D --> E["Outer Tx may continue"]

Scenario 17: RuntimeException vs checked Exception

Scenario: The same transactional method throws either RuntimeException or Exception. What is the interview-level difference?

Answer: Spring's default rollback rules normally roll back for unchecked RuntimeException and Error, but not for checked exceptions. Configure explicit rollback rules when checked exceptions should roll back.

Scenario 18: Checked exception must roll back

Scenario: Your business method throws a checked exception, but the business requirement says the transaction must roll back.

Answer: Use rollbackFor, for example @Transactional(rollbackFor = Exception.class), or another appropriate explicit rollback rule.

@Transactional(rollbackFor = PaymentException.class)
public void pay() throws PaymentException {
    debit();
    throw new PaymentException();
}

Scenario 19: noRollbackFor business warning

Scenario: A business warning should be propagated to the caller, but it should not cause the transaction to roll back.

Answer: If appropriate for the application's exception hierarchy and rollback rules, use noRollbackFor for that exception type.

@Transactional(noRollbackFor = WarningException.class)
public void process() {
    dao.save();
    throw new WarningException();
}

Scenario 20: Exception is swallowed

Scenario: DAO throws an exception, the service catches it, logs it, and returns normally. The developer expects rollback. What is the issue?

Answer: The transaction interceptor decides rollback based on what happens at the transactional boundary. If the exception is swallowed and the method returns normally, automatic rollback may not occur. Explicitly mark rollback-only or rethrow according to the intended design.

Scenario 21: Dirty checking without save()

Scenario: You load a managed employee inside a transaction, change employee.setSalary(...), but never call save(). Can the database still update?

Answer: Yes, with a managed JPA entity, dirty checking can detect the changed state and synchronize it during flush/transaction completion. This is a key JPA concept: managed entity state is tracked by the persistence context.

flowchart LR
A["find()"] --> B["Managed entity"]
B --> C["setSalary()"]
C --> D["Dirty checking"]
D --> E["SQL UPDATE during flush"]

Scenario 22: LazyInitializationException

Scenario: A lazy relationship works inside the transaction but fails when accessed later outside it.

Answer: A lazy association may require an active persistence context to load its data. If the entity is detached and the needed association was not initialized, accessing it can result in LazyInitializationException.

Interview line: “Lazy loading needs an appropriate persistence context; transaction boundaries therefore matter for when lazy data can be initialized.”

Scenario 23: Entity becomes detached

Scenario: What happens to managed entities after the persistence context is cleared or closed?

Answer: They become detached. Changes made to detached objects are no longer automatically tracked by that persistence context. JPA provides merge() to associate state with a managed instance again.

stateDiagram-v2
Managed --> Detached: clear / close
Detached --> Managed: merge()

Scenario 24: persist vs merge

Scenario: An interviewer asks when you use persist() versus merge().

Answer: persist() is for making a new entity instance managed. merge() copies the state of a detached/new entity into a managed instance and returns that managed instance. Do not describe merge as simply “reattaching the same object.”

Scenario 25: CrudRepository removes boilerplate

Scenario: Your application only needs standard create/read/update/delete repository operations. Would you implement all DAO methods manually?

Answer: With Spring Data JPA, extend a suitable repository abstraction such as CrudRepository and let Spring Data provide the common implementation.

public interface EmployeeRepository
        extends CrudRepository<EmployeeEntity, Integer> {
}

Scenario 26: Query method becomes huge

Scenario: A derived repository method becomes a very long name with many conditions. What would you consider?

Answer: Query derivation is convenient for straightforward predicates, but a complex query can become unreadable. Consider @Query or a more suitable query specification/design depending on complexity.

// Readability problem:
findByDepartmentNameAndRoleAndSalaryGreaterThanEqualAnd...

Scenario 27: @Query SELECT works but UPDATE fails

Scenario: A Spring Data @Query SELECT works, but an UPDATE method fails.

Answer: For a modifying JPQL query, use @Modifying and execute it within an appropriate transaction. SELECT and DML repository methods have different semantics.

@Modifying
@Query("UPDATE EmployeeEntity e SET e.salary = :salary WHERE e.role = :role")
int updateSalary(...);

Scenario 28: @Modifying without transaction

Scenario: You add @Modifying, but the application complains because the update is executed without a suitable transaction.

Answer: @Modifying tells Spring Data that the query changes data; it does not by itself replace transaction management. Put the operation inside an appropriate transaction, commonly at the service boundary.

Scenario 29: Positional parameter mismatch

Scenario: Your query uses ?1, but you accidentally treat the second Java argument as the first parameter.

Answer: Positional parameters are tied to method-argument positions. ?1 means the first argument, ?2 the second. Named parameters are often easier to read in larger queries.

Scenario 30: Named parameter mismatch

Scenario: JPQL says :salary, but the method uses @Param("amount").

Answer: The parameter name must match the query parameter name. Use @Param("salary") for :salary.

Scenario 31: Why use orm.xml?

Scenario: An interviewer asks why you might define JPA named-query metadata in orm.xml.

Answer: It externalizes ORM metadata and named queries from the entity source code. It can be useful when metadata is intentionally kept outside Java classes or when working with configuration styles that use XML metadata.

Scenario 32: Local transaction or global transaction?

Scenario: Your Spring Boot service talks to one relational database. Do you immediately need JTA?

Answer: Usually no. For a single database resource, a local transaction manager such as JPA/JDBC transaction management is normally appropriate. Global/JTA transactions become relevant when multiple transactional resources must participate in one coordinated transaction.

flowchart TD
A["One database"] --> B["Local transaction"]
C["Database + JMS + another resource"] --> D["Consider global/JTA coordination"]

Scenario 33: readOnly does not mean magic protection

Scenario: A developer says readOnly=true guarantees that no write can ever happen.

Answer: That is too strong. It expresses read-only intent and can enable optimizations depending on the transaction infrastructure/provider. It should not be treated as a universal database-level write prohibition.

Scenario 34: Transaction timeout exceeded

Scenario: A transactional operation runs longer than its configured timeout.

Answer: The transaction infrastructure can treat the transaction as timed out, leading to rollback/timeout behavior according to the transaction manager and resource environment. Timeout is a transaction boundary control, not simply a Java thread timer.

@Transactional(timeout = 10)
public void longOperation() {
    // Transaction has a 10-second timeout setting.
}

Scenario 35: Repository transaction vs service transaction

Scenario: A repository already has transaction behavior. Why still put the business transaction at the service layer?

Answer: Repository transactions can cover individual repository operations, but the service layer represents the business unit that may combine several operations. The service transaction gives you one explicit boundary around the whole use case.

Scenario 36: Two repositories must succeed together

Scenario: Creating an order requires saving an Order and an OrderAudit record. If either fails, both should be undone. Where is the transaction boundary?

Answer: Put the transaction around the service use case that performs both operations.

flowchart TD
S["@Transactional createOrder()"] --> O["OrderRepository.save"]
S --> A["AuditRepository.save"]
O --> C["Same transaction"]
A --> C
C --> D{"Both succeed?"}
D -->|Yes| E["COMMIT"]
D -->|No| F["ROLLBACK"]

Scenario 37: Audit must survive outer rollback

Scenario: You want an audit record to commit even if the main business transaction later fails.

Answer: This is a classic use case to consider REQUIRES_NEW for the audit operation, provided the separate transaction semantics are actually appropriate. The audit transaction commits independently.

Scenario 38: Which transaction manager should you choose?

Scenario: Your application uses JPA with one database. The interviewer asks which Spring transaction manager is appropriate.

Answer: Use JpaTransactionManager for a single JPA EntityManagerFactory. The general abstraction is PlatformTransactionManager; the concrete implementation depends on the resource technology.

flowchart LR
A["PlatformTransactionManager"] --> B["JpaTransactionManager"]
B --> C["EntityManagerFactory"]
C --> D["JPA transaction"]

Scenario 39: What actually happens around @Transactional?

Scenario: The interviewer asks: “Don't just tell me @Transactional; what happens internally when the method is called?”

Answer: In proxy-based Spring transaction management, the caller invokes the Spring proxy. The transaction interceptor obtains/participates in a transaction through the configured transaction manager, invokes the target method, then commits or rolls back based on the outcome and rollback rules.

sequenceDiagram
participant C as Caller
participant P as Proxy
participant T as TxManager
participant S as Service
C->>P: call service()
P->>T: begin/join
P->>S: target method
S-->>P: result/exception
P->>T: commit/rollback
P-->>C: result/exception

Scenario 40: Full coding-debug scenario

Scenario: You are given this code in an interview:

@Transactional
public void transfer() {
    debitAccount();
    try {
        creditAccount();
    } catch (RuntimeException ex) {
        log.error("Credit failed", ex);
    }
}

Question: The interviewer asks, “Would you expect the debit to roll back automatically?”

Answer: Not necessarily. The exception is caught inside the transactional method and the method can return normally. Spring's interceptor may therefore see successful completion. If the business rule says the entire transfer must fail atomically, do not silently swallow the failure; rethrow it or explicitly mark the transaction rollback-only.

flowchart TD
A["transfer()"] --> B["debit"]
B --> C["credit fails"]
C --> D["Exception caught"]
D --> E["Method returns normally"]
E --> F["Potential commit"]
F --> G["Interview fix: rethrow / mark rollback"]

Golden rule: Always reason from the transaction boundary + propagation + exception outcome, not from the annotation alone.

Interview reasoning formula: Transaction boundary → Propagation → Persistence context/resource → Exception outcome → Rollback rule → Final database state.
